# Android • Канбан спринта

**Цель демо.** Без запущенного Spring Boot пользователь регистрируется, задаёт дату дохода и PIN, создаёт счёт и записывает расход. После перезапуска видны операция, новый баланс, дневной лимит и игровой прогресс. При восстановлении связи локальные изменения попадают в имитацию сервера ровно один раз.

**Как читать карточки.** Каждая строка — одна карточка. Короткое название можно перенести в заголовок, последнюю колонку — в описание и критерии приёмки. В колонке «Опора» указаны результаты, нужные для проверки. Верстку и подготовку примеров можно начинать раньше.

**Как идут данные.** Экран передаёт действие в ViewModel. Правило приложения (use case) проверяет ввод или делает расчёт. Репозиторий читает и записывает данные через DAO — запросы к базе Room на телефоне. Экран подписан на эти данные и обновляется после локальной записи. Отдельно синхронизация обменивается изменениями с API. Для этого спринта предлагается Ktor MockEngine со своим состоянием «сервера», отдельным от Room. Так команда проверит те же запросы и JSON, которые затем получит бэкенд. [Контракт API 1.2](openapi.yaml)

## «Дело дня»

| № | Карточка | Опора | Что сделать и как принять |
|---|---|---|---|
| 22 | Рассчитать дневной лимит на телефоне | 10, 18 | Взять остатки только действующих счетов выбранной валюты с включённым прогнозом. По рабочему правилу из документа 03 лимит равен `max(0, (остаток − резерв) / дни до дохода)`. При резерве 10%, остатке 10 000 ₽ и 10 днях получается 900 ₽ в день. Отдельные проверки — нет даты, разовая дата наступила, подходящих счетов нет, остаток отрицательный. |
| 23 | Показать «Дело дня» на главном и в расходах | 22 | Один компонент и один источник расчёта для двух экранов. После записи расхода, изменения даты или выключения счёта из прогноза обе плашки показывают обновлённое значение. Пустое состояние предлагает доступное действие, например «Указать дату». |

## Что брать в работу сначала

- **Первое демо — сохранение расхода.** Параллельно взять 01 (иконки), 02 (модели), 06 (мок). Дальше 03–05 и 10–14 дают локальную запись, 15–16 делают результат видимым. Для ранней проверки подойдёт тестовая база со счётом и категориями. Для сквозной приёмки использовать регистрацию и первое чтение с мока.
- **Параллельная работа с данными.** После форматов из 02 один участник берёт локальные запросы, другой — обработчики 08–09 с примерами JSON. Разработчик UI уже может работать над формой 13 по состояниям «нет счетов» и «счета загружены». Данные для Compose Preview остаются в превью.
- **Вход и безопасность.** Экран PIN (20) можно брать сразу. Карточки 17–19 объединяются с ним в 21. После 10 и 18 доступен расчёт лимита. Игровая ветка стартует с 24. Отправку и загрузку дельт стоит проверить на одном счёте сразу после 08, затем добавлять остальные сущности.
- **Работа без знания Android.** Участник команды может подготовить пары «запрос → ожидаемый ответ» для 07–09, календарные примеры для 18 и 26, таблицу начислений для 27–28 или провести приёмку 35 на эмуляторе.

## Как разложить карточки по веткам

Для команды предлагаю короткие ветки от актуальной `main`. На одну ветку — один pull request (PR) и один результат, который можно показать на эмуляторе или проверить тестом. Обычно в такой PR помещаются 1–3 карточки. Например, для «Добавить операцию» правило сохранения, поля шторки и её кнопка дают один сценарий и проверяются вместе.

### Как вести работу на доске

**Как начать, если Android ведёт один человек.** Возьми 02–03 как первую ветку с кодом данных. Коллега может параллельно закончить 01, другой — подготовить для 06 и 08–09 примеры запросов и ответов из OpenAPI. После слияния 02–03 возьми 04–05. Дальше у 10–11 и 12–14 общая готовая основа. Для раннего демо удобно сначала создать счёт, затем записать на него расход. Ветки для оставшихся карточек создавайте по мере того, как берёте их в работу.

**Где возможны пересечения.** В 03 и 24 меняется схема Room, поэтому игровую миграцию нужно строить поверх уже слитой финансовой. В 17, 19 и 21 затрагивается навигация. В первых двух PR подключайте экраны своих сценариев, выбор стартового маршрута соберите в 21. Для 16, 23, 29 и 30 удобно держать карточки в отдельных Compose-компонентах, тогда общее изменение в `HomeScreen` сводится к вызовам этих компонентов.

## Что согласовать по ходу спринта

1. **«Дело дня».** В документации описан безопасный дневной ориентир прогноза. В плане он используется и для новой плашки. Резерв 10% — рабочий вариант. До приёмки 22–23 согласовать округление, показывается ли сам лимит или остаток лимита после трат за сегодня, и доступность плашки в первые два дня истории.
2. **Уровни и награды.** В документации заданы базовые начисления, пять титулов и 11 кодов. Таблицу порогов уровней и бонусов, условия двух наград по прогнозу и соответствие названия «Финансовый след» коду нужно зафиксировать вместе с бэкендом. Это не мешает делать локальные таблицы и учёт активных дней.
3. **Переходы.** Строка «Дата поступления» в настройках следует цели спринта. Для корректировки баланса, отметки без трат при скрытой игре и подробной аналитики с «Доходов» документация оставляет открытые вопросы. Восстановление и смена пароля, изменение имени и почты ждут согласования методов API.
