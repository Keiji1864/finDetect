# FinDetect — ИИ-прогноз и советы
Описание фичи и use cases. Актуализация: 10.11.2026.

Общие правила — 01, базовые сценарии — 02. Интерфейс приведён к секциям 01, 05, 06 и 09 дизайна; серверные поля — к openapi.yaml.
Это целевая спецификация: демонстрационные суммы в UI не подтверждают готовность алгоритма или серверной модели.

## 1. Назначение

Помочь ответить: «Хватит ли текущих денег до следующего дохода и какой ориентир расходов выбрать на день?». Прогноз опирается на вручную внесённые данные и помогает планировать, не запрещая операции.

Основной результат в интерфейсе:
- текстовый статус, например «В плане»;
- сколько дней осталось до дохода;
- крупный рекомендуемый ориентир на день;
- 2–3 обоснованных совета;
- отдельное пояснение «Как это работает».

Остаток к дате дохода, диапазон, дата исчерпания средств, уверенность и критичная категория остаются частью расчёта/API. В актуальном макете им не соответствуют дополнительные обязательные крупные карточки в профиле.

## 2. Входные данные

| Данные | Правило |
|---|---|
| Валюта | Выбранная валюта отображения, без конвертации |
| Доступный остаток | Сумма вычисленных балансов действующих счетов этой валюты с `includeInForecast=true` |
| История расходов | Последние 28 дней в той же валюте, по категориям и локальным датам |
| История удалённых счетов | Расходы остаются историческими данными; их текущие остатки исключены |
| Выключенный из прогноза счёт | Остаток исключён; прежние расходы не исчезают из общей истории валюты |
| Следующий доход | Дата и правило повторения, без обязательной суммы |
| Полнота учёта | Активные дни и явные отметки «Сегодня трат не было» |

Если баланс накоплений не должен увеличивать доступные деньги, пользователь выключает этот счёт из прогноза.

Пропуск записи не равен нулю расходов. Отметка дня без трат помогает различать реальный ноль и отсутствие данных. Если позже в тот же день внесён расход, он участвует в расчёте; отметка не должна обнулить его.

День активности для серии определяется моментом ввода. День расхода для статистики определяется датой совершения операции. Внесение сегодня старой покупки не создаёт несколько активных дней задним числом.

## 3. Следующий доход и повторение

Онбординг «Когда следующий доход?» содержит:
- «Следующее поступление»: выбор даты;
- «Повторять»: в макете «Каждый месяц»;
- пояснение, что настройку можно изменить позже;
- «Продолжить» и «Пропустить».

Для текущего дизайна поддерживаются одноразовая дата и ежемесячное повторение по выбранному числу. В API это `CUSTOM_DATE` с `date` либо `MONTHLY` с `dayOfMonth`. Если нужного числа в месяце нет, используется последний день месяца. Например, правило на 31-е в феврале выбирает последний день февраля, а в марте снова 31-е.

Ранее заданные `MONTH_START` и `MONTH_END` сохранены в контракте как правила; отдельные пункты выбора для них в приложенных макетах не раскрыты. Не добавлять невидимый набор вариантов повторения без согласования.

Одноразовая дата после наступления требует нового выбора. Для расчёта нужны дни строго после текущей даты: если доход сегодня, показать состояние наступившей даты и предложить подтвердить/указать следующий доход, не делить на ноль. Регулярное правило после обработки текущей даты вычисляет следующее будущее вхождение.

Настройка хранится локально и синхронизируется через /me/settings. При пропуске хранится `incomeDate=null`; повторно принудительно открывать онбординг нельзя. Маршрут последующего изменения даты в новых макетах настроек нужно уточнить.

## 4. Расчёт на устройстве: уровень 1

Сохраняется прежний подход простых статистических правил. Он нужен для первого рабочего варианта и офлайна.

Обозначения: B — доступный остаток, D — дни до следующего дохода, S — ожидаемый дневной расход.

1. Определить будущую дату дохода и D. Если D ≤ 0, расчёт не выдавать до разрешения даты.
2. По истории до 28 дней оценить дневной расход: усечённое среднее с исключением верхних 10% крупных значений и большим весом свежих дней (ориентир затухания — неделя). При короткой истории использовать доступную и снизить уверенность.
3. Ожидаемые траты: S × D.
4. Ожидаемый остаток: B − S × D.
5. Дата, до которой хватит: сегодня + число полных дней B / S при B > 0 и S > 0.
6. Ориентир на день: max(0, (B − резерв) / D). Рабочий вариант резерва — 10% положительного B.
7. Оптимистичный/осторожный сценарии оцениваются по более низкому/высокому дневному расходу, а не произвольной поправкой текста.
8. Критичная категория: наибольший рост расходов последних 14 дней относительно предыдущих 14; при равном росте — большая сумма.

Параметры усечения, затухания, квантилей и округления должны быть едины у клиента и сервера. Старая документация задавала подход, но не точные константы; значения для реализации нужно зафиксировать вместе с примерами расчёта, не выдавая их за готовую модель.

### 4.1 Статусы

| API | Смысл | Подача |
|---|---|---|
| GREEN | Ожидаемый остаток покрывает запас минимум на 3 дня расходов | «В плане» |
| YELLOW | Остаток неотрицательный, но запас мал, либо осторожный сценарий отрицательный | Спокойное предупреждение и действие |
| RED | Ожидаемый остаток отрицательный | Риск нехватки и конкретный ориентир |

При нулевом остатке нет положительного запаса: он не должен случайно стать зелёным из-за сравнения с нулём. Отрицательный B означает красный риск. При S=0 дата исчерпания не вычисляется (`lastsUntil=null`), деление на ноль исключено. Недостаток данных и нулевой реальный расход — разные состояния.

Статус всегда сопровождается текстом. Кремовая плашка из макета не заменяется автоматически яркой красной/зелёной карточкой: оформление задаёт DESIGN.md.

## 5. Роль сервера и ИИ

Три части:
1. Локальные правила считают числа и работают без сети.
2. Серверная статистическая модель может уточнять дневной расход, сезонность, диапазон и аномалии.
3. Языковая модель формулирует советы по уже рассчитанным фактам.

Языковая модель не назначает собственные суммы, не добавляет неизвестные покупки и не меняет статистический результат. Совет должен опираться на конкретные операции/агрегаты.

На экране используется один согласованный результат целиком:
- до реализации серверной модели и без сети — локальный;
- после успешной синхронизации и получения серверного результата — серверный;
- при ошибке сервера — локальный с понятной пометкой.

Нельзя одновременно показывать дневной ориентир одного расчёта и статус/дату другого. Источник, валюта, дата и выбранные счета относятся к одной версии результата. Старые советы не подписываются как новые.

## 6. Экран «ИИ-прогноз»

Открывается с карточки финансового совета на главном; точный триггер отмечен в DESIGN.md как требующий подтверждения. Уведомление риска также ведёт сюда.

Порядок блоков:
1. Название, стрелка назад.
2. Плашка статуса и дней до дохода.
3. Крупная сумма «Рекомендуемый ориентир на день».
4. Советы: короткий факт, предложение действия, вторичная кнопка «Совет полезен».
5. Строка «Как рассчитан прогноз» → «Как это работает».

Это отдельный экран без нижней навигации. Прогноз не находится в профиле и не дублируется старой полоской риска под шапкой расходов.

На главном советы показываются карточкой с пейджером «1 из 3». На расходах — контекстная карточка по категории, на доходах — сравнение с прошлым периодом. Эти числа вычисляются из данных, а не копируются из макета.

## 7. «Как это работает»

Содержит:
- «Ориентир, а не ограничение» и короткое объяснение;
- «01 · История расходов» — последние 4 недели;
- «02 · Выбранные счета» — количество и сумма остатков;
- «03 · Следующий доход» — вычисленная дата;
- что влияет на результат: регулярность записей и актуальность остатков;
- «Настроить счета» → вкладка «Счета», где у счёта есть «Учитывать в прогнозе».

Количество и сумму выбранных счетов клиент может получить из синхронизированных счетов; отдельного нового серверного поля для этого не требуется. В офлайне пояснение строится по тому же локальному снимку, что и прогноз.

## 8. Минимум данных и состояния

Сохранены прежние целевые пороги:
- меньше 3 активных дней — «Собираем улики: ещё N дней», без выдуманного прогноза;
- 3–6 дней — предварительный результат;
- от 7 активных дней за последние 14 — обычный;
- от 21 активного дня в окне истории — повышенная уверенность.

Серию подряд не путать с количеством доступных дней истории. Длинная серия сама по себе не гарантирует точность, если расходы записаны неполно.

`ForecastAvailability` в API: AVAILABLE, COLLECTING_DATA, NO_INCOME_DATE, INCOME_DATE_PASSED, NO_ACCOUNTS. Если результат недоступен, `forecast=null`, а не сумма 0. Выключение всех счетов также означает NO_ACCOUNTS для прогноза, даже если обычный список счетов не пуст.

Детальные макеты этих состояний не приложены; использовать общие компоненты пустого состояния/подсказки.

## 9. Онлайн и офлайн

Онлайн: сначала отправить нужные операции, остатки и настройку дохода; затем GET /forecast. Числа можно запрашивать с `includeAdvices=false`, тексты — отдельным запросом с `includeAdvices=true`. Параметры `today` и `timeZone` передаёт клиент.

Офлайн: локальный результат с пометкой «Без интернета, упрощённый расчёт». Последние 2–3 сохранённых совета допускаются с датой и признаком устаревания. Если после нового ввода факт совета больше не актуален, его нельзя показывать как текущую рекомендацию.

Изменение операции, корректировка остатка, удаление/выключение счёта, смена валюты и даты дохода пересчитывают прогноз. Сетевая ошибка не блокирует ручной ввод.

## 10. Советы и обратная связь

Примеры из дизайна:
- «Кафе: на 700 ₽ больше» — только если есть корректное сравнение одинаковых интервалов.
- «Подписки: 1 490 ₽ в месяц» — только если найден и обоснован повторяющийся платёж. Ручной учёт не означает автоматического доступа к банковским подпискам.
- «Попробуйте один день с кофе из дома» — действие, связанное с обнаруженным ростом расходов.

Нельзя делать вывод о превышении месячных трат, сравнивая неполный текущий месяц с полным предыдущим без пояснения методики. Нет данных для совета — карточка не заполняется фиктивным текстом.

В актуальном UI под советом одна кнопка «Совет полезен»: она отправляет `rating=USEFUL`. После нажатия — подтверждённое состояние, без повторного начисления чего-либо. `NOT_USEFUL` сохранён в API как поддерживаемое значение, но отдельной кнопки «Нет» в новом макете нет.

Оценка хранится локально и отправляется идемпотентно через PUT /forecast/advices/{adviceId}/feedback. Для временного локального совета без серверного ID не отправлять выдуманный идентификатор; серверная оценка доступна после получения серверного совета.

## 11. Граничные случаи

- Нет даты — предложить указать её, без принуждения.
- Дата наступила/прошла — обновить регулярное правило или запросить следующую одноразовую дату.
- Нет включённых счетов валюты — предложить «Настроить счета».
- Остаток отрицательный — красный риск, ориентир не ниже нуля.
- История без расходов — отличить подтверждённые нулевые дни от неизвестных.
- Крупный новый доход — пересчитать после записи, будущие доходы автоматически не добавлять.
- Другая валюта — отдельный результат, без конвертации.
- Смена счетов во время запроса — устаревший ответ не заменяет результат для нового набора.
- Советы отключены — числа и пояснение остаются. Точка управления советами в новых настройках требует дополнения.

## 12. Данные и границы реализации

API уже описывает дату дохода, счета с `includeInForecast`, прогноз, пояснение и оценки. Ежемесячное правило добавлено при этой актуализации, существующие правила сохранены.

Наличие контракта не означает готовность сервера. Слой данных, хранение кеша, фоновые задачи и миграции реализуются после проверки текущего проекта; утверждения «WorkManager уже есть» или «такой use case уже написан» из старого документа не используются как факт.

P0: настройка даты и ежемесячного повтора, локальные числа, состояния недостатка данных, отдельные экраны прогноза и пояснения.
P1: серверный расчёт и советы, их кеш, оценка полезности, уведомление риска.
Дальнейшее улучшение: уточнённая сезонность и распознавание повторяющихся платежей. Карточка подписок уже есть в дизайне; до готовности детектора её можно показывать только в демонстрационном режиме с явным статусом моковых данных.

## Use cases

### UC-23. Выбор даты дохода

Онбординг → «Когда следующий доход?».
1. Указать дату и повторение.
2. «Продолжить» сохраняет настройку локально, ставит её в синхронизацию, пересчитывает будущую дату.
3. «Пропустить» сохраняет отсутствие настройки.
4. После первого шага перейти к созданию PIN, затем на главный.

Позднее настройку можно менять; конкретный маршрут редактирования пока не показан в новых макетах. До появления отдельного решения не добавлять скрытые переходы в профиле. Работает офлайн после входа, на сервер уходит позже.

### UC-26. Просмотр прогноза

1. Открыть «ИИ-прогноз» с главного.
2. Показать статус, дни до дохода, ориентир, советы.
3. Если данных недостаточно, вместо суммы показать причину и доступное действие.
4. «Как рассчитан прогноз» открывает «Как это работает».
5. «Настроить счета» переводит к счетам; после изменения набора результат обновляется.

Онлайн — синхронизация и серверный результат; офлайн — локальный расчёт и отмеченные сохранённые советы.

### UC-26A. Уведомление риска

Сохранённое целевое требование, отдельного нового макета нет.
Фоновый пересчёт обнаруживает переход в YELLOW/RED; при достаточной истории (от 7 активных дней) показывает спокойное предупреждение с действием. Не чаще раза в два дня, с учётом разрешения и общих ограничений уведомлений из 04. Нажатие открывает «ИИ-прогноз» после PIN при необходимости.

### UC-26B. «Совет полезен»

Нажатие под конкретным серверным советом сохраняет USEFUL локально и отправляет оценку при сети. Повторное нажатие не создаёт дублей. Ошибка сети сохраняет очередь. В интерфейсе из макета нет обязательной кнопки отрицательной оценки.
